# standarts — универсальные правила работы с проектом ПЛК

> Единый свод правил, по которому AI-агент пишет, проверяет и сопровождает код проекта
> на ПЛК Siemens. Документ самодостаточен и переносится в любой проект без правок:
> всё проектное (задача, имена, адреса, оборудование) приходит из задания проекта.

## 0. Как пользоваться этими правилами

### 0.1 Порядок чтения проекта (в каждом новом чате)

1. **Задание проекта** — документ с требованиями (обычно `README.md` или ТЗ в корне
   репозитория). Это **единственный источник требований**: что делает система, какие
   сигналы, какие режимы, какие ограничения и что считается успехом.
2. **Эти правила** — как писать код, как его проверять и чего не делать.
3. **Реализация** — исходники блоков (`*.scl`, `*.db`, `*.udt`) и таблицы PLC-тегов (`*.xml`).

Не додумывать проект «по аналогии»: если требование или имя не найдены в файлах —
прочитать файлы полностью или уточнить у пользователя. Догадка, выданная за факт,
дороже одного вопроса.

### 0.2 Приоритет источников

| Вопрос | Что главнее |
| ------ | ----------- |
| Поведение системы, сигналы, режимы | задание проекта |
| Стиль, структура, порядок вызовов, проверки | этот файл |
| Существующие имена блоков, тегов, DB | проект TIA и задание |
| Наличие инструкции, типа или блока в платформе | документация платформы |

Расхождение кода с заданием — **дефект**, а не новая норма: о нём сообщают пользователю,
а не подгоняют правила под написанное молча. Расхождение этого файла с платформой — тоже
повод сказать прямо, а не «сделать как получится».

### 0.3 Инструментарий агента

- Оболочка — PowerShell (`powershell.exe`, Windows); пути абсолютные, в одинарных кавычках.
- Обзор файлов:
  `Get-ChildItem -LiteralPath '<корень проекта>' -Recurse -File | Where-Object { $_.FullName -notlike '*\.git\*' }`.
- Содержимое — инструментом чтения файлов; поиск по шаблонам — поиском по коду (regex).
- Независимые чтения, поиски и команды отправлять параллельно в одном ответе.
- `cmd /c` и сложные пайпы не использовать; `git` запускать с `--no-pager`.
- Компиляция и запуск — только в GUI TIA Portal: из терминала проект не собирается.
- Проверка исходников без TIA (доступное из терминала): парность `BEGIN` / `END_*`,
  отсутствие табов и строк из одних пробелов, совпадение имён блоков с именами файлов,
  наличие всех используемых тегов в таблице тегов. Это фильтр грубых ошибок, а не сборка.

### 0.4 Типы файлов в репозитории

| Что | Расширение | Роль |
| --- | ---------- | ---- |
| Исходник блока или типа данных | `*.scl`, `*.db`, `*.udt` | импортируется в TIA как внешний источник, затем «Generate blocks from source» |
| Таблица PLC-тегов | `*.xml` | импортируется в TIA как таблица тегов |
| Задание, карта сигналов, циклограммы | `*.md` | требования и документация |
| Правила для агента | `.clinerules/*.md` | этот файл |
| Проект TIA | `*.ap1x`, `*.zap1x` | как правило, в git не хранится |

Следствия: имена в исходниках должны совпадать с именами в проекте TIA; после правки
таблицы тегов её нужно импортировать заново; после правки `*.scl`/`*.db` блок нужно
генерировать заново, иначе в проекте останется прежняя версия; порядок импорта —
от зависимостей к зависимым (типы данных → блоки → DB → OB → таблица тегов).

### 0.5 Чего агент не делает

- не создаёт и не собирает проект TIA из терминала, не генерирует `*.ap1x`;
- не переименовывает блоки, теги и адреса без согласования — это ломает связь с проектом;
- не добавляет теги и адреса, которых нет в задании и в конфигурации оборудования;
- не подключает сторонние библиотеки: доступны МЭК 61131-3 и штатные блоки TIA;
- не пишет код в стиле CoDeSys (см. раздел 2);
- не оставляет в репозитории временные файлы, созданные для проверок.

### 0.6 Как отчитываться о работе

Коротко и проверяемо: **что** изменено (файл → суть), **чем** проверено (что запускалось
и что показало), **что осталось** сделать в GUI TIA, **какие ограничения** у решения.
Осознанное отступление от правил называется прямо, вместе с причиной.

## 1. Режимы работы агента

Режим выбирается по формулировке запроса; при смене темы режим объявляется.

### codechat — основной код-чат

Написание, правка, рефакторинг, отладка кода; ответы по платформе.

### reviewer — код-ревью

Поиск дефектов и антипаттернов, проверка соответствия этим правилам, предложения
с пояснениями. Ревью не переписывает код без запроса: сначала перечень замечаний
с приоритетами (дефект / нарушение стиля / улучшение).

### architect — архитектор

Проектирование структуры: слои, модули, обмен сигналами, диаграммы (Mermaid), сравнение
вариантов с trade-off. Итог — схема и перечень решений, а не готовый код.

### plc-engineer — инженер по аппаратной части

Конфигурация оборудования TIA (CPU, модули DI/DQ/AI/AO), карта адресов I/O, схемы
подключения, поведение при старте и при переходе STOP→RUN, вопросы безопасности.
Зона ответственности — «железо» и его отображение в проекте, не алгоритмы.

### st-designer — дизайнер кода SCL

Разработка и анализ именно SCL: синтаксис, типы, экземпляры, читаемость, соответствие
МЭК 61131-3 и стилю раздела 3.

## 2. Платформа: TIA Portal

Проект ведётся в TIA Portal (STEP 7 + WinCC) для S7-1200 / S7-1500, язык — SCL.
Конструкции CoDeSys в TIA либо отсутствуют, либо не импортируются: использовать их нельзя.

| Понятие | CoDeSys v3 (не использовать) | TIA Portal (использовать) |
| ------- | ---------------------------- | ------------------------- |
| Глобальные переменные | `GVL.Name` | таблица PLC-тегов, обращение `"TagName"` |
| Точка входа | `PROGRAM PLC_PRG` | циклический организационный блок OB1 |
| Циклическая задача | `MAIN_CYCLE` | цикл сканирования OB1 |
| Тело блока | без `BEGIN` / `END_...` | обязательно `BEGIN … END_FUNCTION_BLOCK` |
| Привязка к адресу | `AT %I0.0` в объявлении | адрес в столбце «Адрес» таблицы PLC-тегов |
| Локальная переменная | `Start` | `#Start` |
| Глобальная переменная | `GVL.Start` | `"TagName"` или `"Global_DB".Field` |
| Вложенный FB | `fb1 : FB_Name;` | `#fb1 : "FB_Name";` (multi-instance в `VAR`) |
| Экземплярный DB | — | single-instance DB, вызов `"FB_Name_DB"();` |
| Ретентивность | `VAR_GLOBAL RETAIN` | retentive-память CPU / `RETAIN` в DB; PLC-теги не retentive |
| Пользовательский тип | `TYPE … STRUCT` | `TYPE "Udt_Name" … END_TYPE` (PLC data type) |
| Исходник | `*.st` | `*.scl` (+ `*.db`, `*.udt`) |
| Сборка | Build → Generate Code | `Ctrl+B` (Compile → Software rebuild all) |
| Отладка значений | Force (F7) / Write | Watch table: `Modify now`, `Force job`, Trace |

Платформенные факты, влияющие на код:

- блоки по умолчанию оптимизированные (`S7_Optimized_Access := 'TRUE'`): доступ к полям DB
  только по именам, абсолютных смещений нет;
- глобальные данные — это PLC-теги и DB; `VAR_GLOBAL` / `GVL` не существуют;
- таймеры, счётчики и edge-детекторы требуют экземпляр (multi-instance в `VAR` или
  отдельный instance-DB) и вызываются каждый цикл;
- `VAR_TEMP` между вызовами не сохраняется: состояние живёт в статических `VAR`;
- «Force» в TIA — это force job: снимается `Force → Delete all force jobs` либо переводом
  CPU в STOP; после отладки его обязательно снимать;
- набор инструкций и системных блоков зависит от CPU и версии прошивки: перед использованием
  нетиповой инструкции проверять её наличие для конкретного CPU и версии TIA;
- версию TIA, тип CPU, версию прошивки и адреса модулей агент берёт из задания или
  уточняет у пользователя — «по умолчанию» эти факты не выдумываются.

## 3. Стиль кода и соглашения (SCL)

### 3.1 Общие правила

- Код — SCL для TIA Portal по МЭК 61131-3; инструкции — стандартные, плюс штатные
  IEC-блоки (раздел 4).
- Обращение к локальному — `#name`, к глобальному — `"Name"`. Смешивать нельзя.
- Никаких «магических чисел»: уставки, задержки, пределы — в `VAR CONSTANT`.
- Промежуточные переменные — только если улучшают читаемость.
- Комментарии `//` — для неочевидной логики и назначения блока; очевидное не комментируется.
- Отступ — 4 пробела, табы не использовать; строки из одних пробелов не оставлять.
- Идентификаторы — только латиница. Кириллица допустима в комментариях и документации.
  Язык комментариев — язык документации проекта (для русскоязычных проектов — русский).
- Длинную логику группировать `REGION … END_REGION`.
- Один блок — одна ответственность; блок длиннее ~200 строк делить.
- Строка — до ~120 символов; длинные вызовы разбивать по параметрам (по одному в строке).
- Порядок и «форматирование» экспортированного кода TIA не ломать без причины: правки
  минимальные, чтобы diff оставался читаемым.

### 3.2 Именование

Соглашения ниже — **значения по умолчанию**. Если в проекте уже есть свои имена, следуем
проекту (переименование без согласования запрещено), а новые сущности называем по правилам.

- Локальные и статические переменные — с маленькой буквы: `startSignal`, `rtStopSignal`.
- Входы/выходы FB, блоки, DB, глобальные теги — с большой буквы: `StartSignal`, `Hmi_DB`.
- Имя файла исходника = имя блока: файл `LogicDevice.scl` содержит
  `FUNCTION_BLOCK "LogicDevice"`.
- Один технологический объект — один оркестратор; модули внутри называются по своей роли.
- Кириллица в идентификаторах запрещена всегда.
- Имя должно отвечать на вопрос «что это», а не «где это»: `MotorRun`, не `Q0_0`.

Префиксы сигналов (по умолчанию):

| Префикс | Тип сигнала | Пример |
| ------- | ----------- | ------ |
| `DI_` | дискретный вход | `DI_ButtonStart` |
| `DO_` | дискретный выход | `DO_MotorRun` |
| `AI_` / `AO_` | аналоговый вход / выход | `AI_Level` |
| `HMI_` | сигнал панели оператора без физического адреса | `HMI_LampFault` |
| `Cmd_` / `Sts_` | команда / статус (внутренние данные) | `CmdStart`, `StsRunning` |

Суффиксы блоков (по умолчанию):

| Суффикс | Тип | Пример |
| ------- | --- | ------ |
| `_DB` | data block (global или instance) | `Hmi_DB`, `UnitMain_DB` |
| `_InOut` | таблица PLC-тегов | `Tags_InOut` |
| — | function block / function | `UnitMain`, `AlwaysOn` |
| — | организационный блок | имя как в проекте (обычно `Main`) |

Ролевые имена модулей (рекомендуемые, если в задании нет других): `HardwareInput`,
`HardwareOutput`, `LogicDevice`, `HMIInterface` — см. раздел 8.

### 3.3 Порядок секций в FB

1. `VAR_INPUT` — входы
2. `VAR_OUTPUT` — выходы
3. `VAR_IN_OUT` — параметры по ссылке
4. `VAR` — статические (живут в instance-DB): таймеры, счётчики, вложенные FB
5. `VAR_TEMP` — временные
6. `VAR CONSTANT` — константы

Тело — после `BEGIN`; блок закрывается `END_FUNCTION_BLOCK` / `END_FUNCTION` /
`END_ORGANIZATION_BLOCK` / `END_DATA_BLOCK`.

Эталон объявления:

```scl
FUNCTION_BLOCK "LogicDevice"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_INPUT
      Enable : Bool;
   END_VAR
   VAR_OUTPUT
      Active : Bool;
   END_VAR
   VAR
      rtEnable : R_TRIG;
   END_VAR

BEGIN
    // назначение блока — одной строкой выше логики
    #rtEnable(CLK := #Enable);
    #Active := #rtEnable.Q;
END_FUNCTION_BLOCK
```

### 3.4 Правила Function Block

- Вызывать **каждый цикл и безусловно**: таймеры, счётчики и edge-детекторы хранят состояние
  в экземпляре; вызов внутри `IF` «замораживает» их `Q` и `ET`.
- Не мутировать `VAR_INPUT`: работать с локальной копией.
- Инициализировать статические `VAR`: `state : Int := 0;`.
- `RETAIN` — осознанно: уставки и накопленные счётчики — да; состояние триггеров и команды
  механизмов — нет (требование безопасного старта после STOP→RUN).
- Выходные параметры забирать через `=>` в вызове блока.
- Вложенные FB объявлять в `VAR` (multi-instance); отдельный instance-DB нужен только
  блокам, вызываемым из OB или из нескольких мест.
- Состояние алгоритма — в статических `VAR`, никогда в `VAR_TEMP` или в M-битах.
- Блок не обращается к тегам и DB, если его роль — чистая логика: всё нужное приходит
  через параметры (см. раздел 5).
- Один и тот же FB нельзя вызывать «дважды за цикл» с одним экземпляром: второй вызов
  перезапишет состояние первого.

### 3.5 Правила работы с тегами (замена GVL)

- Все физические I/O — только в таблице PLC-тегов: осмысленное имя + абсолютный адрес.
- Из кода — только символьные имена; прямая адресация (`%I0.0`, `%Q0.0`) в логике —
  антипаттерн.
- Абсолютные адреса должны совпадать с конфигурацией оборудования. При изменении карты
  адресов синхронно правятся таблица тегов, задание и настройки внешних клиентов.
- Сигналы, существующие только на панели оператора, не садятся на физический `%Q`:
  это поля DB или теги `HMI_*` без адреса.
- Внутренние данные (состояния, счётчики, индикация) хранятся в DB, а не в I/O-тегах.
- Правка таблицы тегов — изменение проекта: после правки `*.xml` таблицу импортируют в TIA,
  иначе код не скомпилируется (тег «не найден») или будет читать старое.
- Тег с одним писателем (см. 3.6): если сигнал формируется программой, внешний клиент его
  только читает, и наоборот.

### 3.6 Внешние клиенты: панель, SCADA, эмулятор поля, OPC UA

Поле и панель могут читать и писать теги ПЛК напрямую. Правила не зависят от конкретного
продукта и формулируются как контракт обмена:

- внешние клиенты работают по символическим именам (OPC UA) или по абсолютным адресам
  (S7 / PUT-GET), поэтому имена тегов и карта адресов — часть контракта, а не «внутреннее дело»;
- **один тег — один писатель**: если тег пишет внешний клиент, программа в него не пишет,
  и наоборот. Двойная запись даёт «плавающие» ошибки;
- права доступа к тегу извне (`hmiVisible` / `hmiAccessible` / `hmiWriteable` или аналог
  в конкретной версии TIA) открываются только там, где это нужно для обмена, и это
  фиксируется в задании. Занижение прав ломает обмен, завышение — снижает защищённость;
- доступ по S7/PUT-GET требует разрешения в свойствах CPU
  (`Protection & Security → Connection mechanisms`); OPC UA — включённого сервера и
  поддержки прошивкой;
- при изменении карты адресов синхронно правится конфигурация клиента: иначе он пишет
  в «чужой» адрес, и это выглядит как ошибка логики;
- запись в дискретные входы из таблицы наблюдения обычно перетирается образом входов:
  для имитации входов используются средства симулятора/эмулятора, а не `Modify now`;
- после отладки с принудительной записью (Force) проверяется, что задания силы сняты.

## 4. Стандартные IEC-блоки — когда использовать

Все они требуют экземпляр и вызываются **каждый цикл**, безусловно.

### 4.1 Таймеры

| FB | Когда использовать | В SCL |
| -- | ------------------ | ------ |
| `TON` | задержка старта, антидребезг, контроль времени | `#tonStart(IN := #start, PT := TIME#2S);` → `#tonStart.Q` |
| `TOF` | задержка стопа, удержание аварии | `#tofAlarm(IN := #fault, PT := TIME#10S);` |
| `TP` | импульс фиксированной длительности | `#tpPulse(IN := #trig, PT := TIME#500MS);` |
| `TONR` | накопление времени | `#tonrRun(IN := #run, R := #reset, PT := TIME#1H);` |

### 4.2 Счётчики

| FB | Когда использовать |
| -- | ------------------ |
| `CTU` | счётчик деталей, циклов |
| `CTD` | обратный отсчёт |
| `CTUD` | балансировка, контроль уровня |

### 4.3 Edge-детекторы

| FB | Когда использовать |
| -- | ------------------ |
| `R_TRIG` | нажатие кнопки, начало события (передний фронт) |
| `F_TRIG` | отпускание, конец события (задний фронт) |

### 4.4 Бистабильные элементы

| Функция | Когда использовать |
| ------- | ------------------ |
| `SR` | доминирует установка (инструкция LAD/FBD в TIA) |
| `RS` | доминирует сброс — безопаснее для команд «стоп» и «авария» |

> В SCL бистабильный элемент пишется выражением с самоподхватом — так приоритет сброса
> виден прямо в коде: `#out := (#set OR #out) AND NOT #reset;`
>
> Уровневый сброс годится только тогда, когда удержание сигнала сброса действительно
> запрещает повторный пуск. Если по заданию событие одноразовое (деталь прошла датчик,
> кнопка нажата), сброс делается по фронту через `R_TRIG`: сигнал, оставшийся включённым,
> не должен блокировать следующий цикл.

## 5. Архитектурные паттерны

### 5.1 Слои приложения (база для любой задачи)

Задача раскладывается на слои с одной ответственностью:

| Слой (роль) | Ответственность | Чего не делает |
| ----------- | --------------- | -------------- |
| Оркестратор | вызывает слои в заданном порядке, связывает их сигналами | не обращается к тегам и DB |
| Модуль входа (`HardwareInput`) | читает полевые сигналы, нормализует (НЗ/НР, масштаб, достоверность) | не содержит логики, ничего не пишет |
| Модуль выхода (`HardwareOutput`) | пишет команды в полевые выходы | не читает и не решает |
| Модуль логики (`LogicDevice`) | алгоритм и состояния | не знает про теги, датчики и механизмы |
| Модуль ЧМИ (`HMIInterface`) | читает команды панели, пишет данные панели | не управляет механизмами напрямую |

Обмен между слоями — простыми типами (`Bool`, `Int`, `Real`, `Time`) через
`VAR_INPUT` / `VAR_OUTPUT`. Пакетный STRUCT для передачи данных между слоями не применять:
STRUCT/UDT допустим для конфигурации, уставок и «сырых» данных внешнего протокола.

Смысл разделения: смена CPU, модулей ввода-вывода или панели затрагивает только
hardware-модули и модуль ЧМИ; логика остаётся неизменной. Если задача маленькая, слои
могут быть «тонкими», но роли не смешиваются.

### 5.2 Порядок вызовов в главном блоке

1. Чтение входов
2. Технологическая логика
3. Запись выходов
4. Режимы работы
5. Обработка ошибок и безопасности
6. Обмен с панелью оператора

Порядок задаётся **в оркестраторе**, а не в OB: OB содержит единственный вызов оркестратора
и больше ничего. Так порядок слоёв не зависит от того, кто и когда правил OB.

### 5.3 Машина состояний (State Machine)

- `CASE #state OF` для переходов; состояние — статическая `VAR` с инициализацией.
- Явно обрабатывать состояния `Idle` / `Run` / `Fault` / `Reset`.
- Выходы выставлять в каждом состоянии либо один раз после `CASE` по состоянию — но не
  «забывать» ни в одном.
- Переходы — только по событиям (фронты, условия); «прыжков» через состояния не делать.
- Номера состояний — в `VAR CONSTANT`, а не «магическими» числами в `CASE`.
- Ветка `ELSE` у `CASE` обязательна: неизвестное состояние не должно оставлять выходы
  в произвольном виде.

### 5.4 Обработка ошибок

- Применять, когда задание требует диагностики.
- Выходы: `ErrorActive : Bool`, `ErrorCode : Int` (0 — нет ошибки).
- Источники: таймаут ожидаемого события (`TON`), противоречивые сигналы датчиков,
  недостоверные значения.
- Квитирование — отдельный вход `Reset` по фронту, не самосброс.
- Ошибка не «залипает» навсегда без пути квитирования и не исчезает молча при
  самопроизвольном восстановлении сигнала, если это не оговорено заданием.
- Диагностика не заменяет безопасность: аварийный останов выполняется аппаратно,
  программный слой его только отражает.

## 6. Цикловое выполнение

- OB1 выполняется циклически сам — вызывать его вручную не нужно.
- Все FB вызывать каждый цикл сканирования, включая таймеры, счётчики и edge-детекторы.
- Цикл не блокировать: никаких `WHILE TRUE`, длинных `FOR` и ожиданий внутри OB.
- Состояние — в статических `VAR` (instance-DB), не в `VAR_TEMP`.
- Не полагаться на порядок вызовов внутри OB, кроме явно заданного оркестратором.
- Время цикла контролировать: длинная логика → увеличивается время сканирования →
  «дрожат» таймеры и фронты. Тяжёлые расчёты переносятся в циклические прерывания
  или оптимизируются.
- Асинхронные задачи (OB циклических прерываний, OB запуска, OB ошибок) применяются
  осознанно и описываются в задании: их взаимодействие с OB1 — источник тонких ошибок.

## 7. Язык SCL — справочник

### 7.1 Синтаксис

- Ключевые слова: `ORGANIZATION_BLOCK`, `FUNCTION_BLOCK`, `FUNCTION`, `DATA_BLOCK`,
  `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT`, `VAR_TEMP`, `VAR`, `VAR CONSTANT`, `END_VAR`,
  `BEGIN`, `END_...`
- Комментарии: `// однострочный` и `(* многострочный *)`
- Разделитель инструкций: `;` — обязателен
- Присваивание: `:=`; сравнение: `=`, `<>`, `<`, `>`, `<=`, `>=`
- Логические: `AND`, `OR`, `NOT`, `XOR`; арифметика: `+`, `-`, `*`, `/`, `MOD`
- Константы: `TRUE`, `FALSE`; литералы — `16#FF`, `2#1010_1010`, `1.5`, `INT#10`,
  `TIME#5S`, `T#1H30M`
- Регистр не важен, но имена блоков и тегов пишутся ровно как в проекте

### 7.2 Базовые типы данных TIA Portal

| Тип | Диапазон | Размер |
| --- | -------- | ------ |
| `Bool` | TRUE / FALSE | 1 бит |
| `Byte` | 0..255 | 8 бит |
| `Word` | 0..65535 | 16 бит |
| `DWord` | 0..4294967295 | 32 бита |
| `SInt` | −128..127 | 8 бит |
| `Int` | −32768..32767 | 16 бит |
| `DInt` | −2^31..2^31−1 | 32 бита |
| `USInt` / `UInt` / `UDInt` | 0..255 / 0..65535 / 0..4294967295 | 8 / 16 / 32 бита |
| `Real` | ±3.4E±38 | 32 бита (IEEE 754) |
| `LReal` | ±1.7E±308 | 64 бита |
| `Time` | `TIME#…` | 32 бита (мс) |
| `Char` / `String` | 1 символ / до 254 символов | — |
| `DTL` | дата и время | 12 байт |

Приведение типов — всегда явное: `INT_TO_REAL()`, `REAL_TO_INT()`, `ROUND()`, `TRUNC()`,
`TIME_TO_DINT()`. Неявные приведения — источник ошибок округления и переполнения.
Для счётчиков и уставок выбирать тип по диапазону, а не «всегда `Int`».

### 7.3 Обращение к данным

| Что | Синтаксис | Пример |
| --- | --------- | ------ |
| Локальная переменная блока | `#name` | `#startSignal := TRUE;` |
| Вход/выход FB | `#name` | `#RunCmd := FALSE;` |
| PLC-тег | `"TagName"` | `"DO_MotorRun" := #cmdRun;` |
| Поле global-DB | `"DbName".Field` | `"Hmi_DB".LampRun := #runCmd;` |
| Поле структуры в DB | `"DbName".Struct.Field` | `"Cfg_DB".Motor.Speed := 1.5;` |
| Экземпляр вложенного FB | `#instance.Output` | `#logic.RunCmd` |
| Меркер (только при необходимости) | `"M_Flag"` или `%M10.0` | `"M_Reset" := TRUE;` |

Правило: `#` — только для локального и статического, кавычки — только для глобального.

### 7.4 Вызов блоков

```scl
// FB с single-instance DB (обычно из OB)
"UnitMain_DB"();

// Вложенный FB (multi-instance) — объявлен в VAR
#hardIn();
#logic(StartSignal := #hardIn.StartSignal,
       StopSignal  := #hardIn.StopSignal);
#hardOut(RunCmd := #logic.RunCmd);

// Выход через =>
#logic(StopSignal := #stopSignal, RunCmd => #runCmd);

// FC
#alwaysOn();

// Стандартный IEC-блок
#tonStart(IN := #cmdRun, PT := TIME#2S);
#rtStopSignal(CLK := #stopSignal);
#ctuCount(CU := #rtStopSignal.Q, R := #reset, PV := 100);
```

### 7.5 Управляющие конструкции

```scl
// Ветвление
IF #a AND NOT #b THEN
    #out := TRUE;
ELSIF #a THEN
    #out := FALSE;
ELSE
    #out := FALSE;
END_IF;

// Машина состояний
CASE #state OF
    0:  // Idle
        IF #startCondition THEN
            #state := 10;
        END_IF;
    10: // Run
        IF #stopCondition THEN
            #state := 20;
        END_IF;
    20: // Wait / Stopped
        IF #resetCondition THEN
            #state := 0;
        END_IF;
ELSE
    #state := 0;
END_CASE;

// Цикл
FOR #i := 0 TO 7 DO
    #sum := #sum + #arr[#i];
END_FOR;

// Группировка
REGION Inputs
    #hardIn();
END_REGION
```

### 7.6 Частые ошибки компиляции в TIA

| Сообщение / симптом | Причина |
| ------------------- | ------- |
| «Не удаётся найти тег …» | тега нет в таблице тегов или имя в коде не совпадает с проектом |
| «Адрес %I0.0 не существует» | нет модуля/канала с таким адресом в конфигурации оборудования |
| «Тип … неизвестен» | не сгенерирован FB/UDT, от которого зависит блок (порядок импорта) |
| «Экземпляр не объявлен» | FB вызван без экземпляра или без `#` |
| «Экземпляр уже используется» | один instance-DB на два вызова одного FB |
| «Недопустимая запись в константу/вход» | попытка присвоить `VAR_INPUT` или `VAR CONSTANT` |
| «Отсутствует `END_...`» | потерян `BEGIN` / `END_FUNCTION_BLOCK` при правке исходника |
| Блок компилируется, но «ничего не работает» | блок не вызывается, либо вызывается внутри условия, либо перекрыт вторым вызовом |

Порядок разбора ошибок: сначала «тип неизвестен» и «тег не найден» (остальные ошибки часто
их следствие), затем синтаксис блока, затем логика.

> Имена в этом разделе — **ролевые заглушки**. В проекте берутся имена из задания;
> если задание имена не фиксирует, используются эти.

### 8.1 Структура репозитория

```
<корень проекта>/
├── Main.scl                   ← циклический OB: только вызов оркестратора
├── Tags_InOut.xml             ← таблица PLC-тегов
├── <Объект>/                  ← технологический объект (по одному на объект/установку)
│   ├── UnitMain.scl           ← оркестратор
│   ├── UnitMain_DB.db         ← его single-instance DB
│   ├── HardwareInput.scl      ← модуль входа
│   ├── HardwareOutput.scl     ← модуль выхода
│   ├── HMIInterface.scl       ← модуль ЧМИ
│   ├── Hmi_DB.db              ← global-DB данных панели (если нужны)
│   └── Logic/
│       └── LogicDevice.scl    ← технологическая логика
├── README.md                  ← задание проекта
└── .clinerules/standarts.md   ← этот файл
```

Правила структуры: подпапка — только если она что-то группирует (например, `Logic/`);
один файл — один блок; DB лежит рядом с блоком, которому принадлежит.

### 8.2 Принципы

1. **Нет STRUCT-посредников** между слоями — только простые типы.
2. **Оркестратор — чистый**: ни одного обращения к PLC-тегам и DB.
3. **Модуль входа** — только читает входные теги, ничего не пишет.
4. **Модуль выхода** — только пишет выходные теги, ничего не читает.
5. **Модуль логики** — не знает про теги, датчики и механизмы.
6. **Модуль ЧМИ** — только читает команды панели и пишет в DB панели.
7. **Портируемость**: смена ПЛК или панели затрагивает только hardware-модули, ЧМИ
   и конфигурацию оборудования.

### 8.3 Роли блоков

| Блок | Ответственность |
| ---- | --------------- |
| циклический OB | точка входа: единственный вызов оркестратора |
| `UnitMain` | оркестратор: вход → логика → выход → ЧМИ |
| `HardwareInput` | чтение полевых сигналов, нормализация |
| `HardwareOutput` | запись команд в полевые выходы |
| `LogicDevice` | алгоритм и состояния |
| `HMIInterface` | лампы и кнопки панели |
| `Hmi_DB` | данные только для панели, без адресов I/O |

### 8.4 Порядок импорта в TIA

типы данных (`UDT`) → FB логики и hardware → оркестратор → global-DB (например, `Hmi_DB`)
→ single-instance DB оркестратора → OB → таблица тегов.

Нарушение порядка даёт «тип не найден». После правки любого исходника — повторная
генерация блока из источника и пересборка проекта.

### 8.5 Эталоны кода

**Циклический OB**

```scl
ORGANIZATION_BLOCK "Main"
TITLE = "Main Program Sweep (Cycle)"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1

BEGIN
    // единственный вызов: оркестратор делает всё остальное
    "UnitMain_DB"();
END_ORGANIZATION_BLOCK
```

**Оркестратор**

```scl
FUNCTION_BLOCK "UnitMain"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR
      hardIn  : "HardwareInput";
      logic   : "LogicDevice";
      hardOut : "HardwareOutput";
      hmi     : "HMIInterface";
   END_VAR

BEGIN
    #hardIn();

    #logic(StartSignal := #hardIn.StartSignal,
           StopSignal  := #hardIn.StopSignal);

    #hardOut(RunCmd := #logic.RunCmd);

    #hmi(MachineRun   := #logic.RunCmd,
         MachineFault := FALSE);
END_FUNCTION_BLOCK
```

**Модуль входа (нормализация НЗ)**

```scl
FUNCTION_BLOCK "HardwareInput"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_OUTPUT
      StartSignal : Bool;
      StopSignal  : Bool;
   END_VAR

BEGIN
    // датчик НЗ: 0 на входе = «событие обнаружено»
    #StartSignal := NOT "DI_Sensor1";
    #StopSignal   := NOT "DI_Sensor2";
END_FUNCTION_BLOCK
```

**Модуль выхода**

```scl
FUNCTION_BLOCK "HardwareOutput"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_INPUT
      RunCmd : Bool;
   END_VAR

BEGIN
    "DO_MotorRun" := #RunCmd;
END_FUNCTION_BLOCK
```

**Модуль логики (самоподхват + сброс по фронту)**

```scl
FUNCTION_BLOCK "LogicDevice"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_INPUT
      StartSignal : Bool;
      StopSignal  : Bool;
   END_VAR
   VAR_OUTPUT
      RunCmd : Bool;
   END_VAR
   VAR
      rtStopSignal : R_TRIG;
   END_VAR

BEGIN
    #rtStopSignal(CLK := #StopSignal);

    // пуск по уровню (самоподхват), останов — по фронту события
    #RunCmd := (#StartSignal OR #RunCmd) AND NOT #rtStopSignal.Q;
END_FUNCTION_BLOCK
```

**DB панели и модуль ЧМИ**

```scl
DATA_BLOCK "Hmi_DB"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
NON_RETAIN
   VAR
      LampRun   : Bool;
      LampFault : Bool;
   END_VAR

BEGIN
END_DATA_BLOCK
```

```scl
FUNCTION_BLOCK "HMIInterface"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_INPUT
      MachineRun   : Bool;
      MachineFault : Bool;
   END_VAR

BEGIN
    "Hmi_DB".LampRun  := #MachineRun;
    "Hmi_DB".LampFault := #MachineFault;
END_FUNCTION_BLOCK
```

### 8.6 Антипаттерны структуры

- оркестратор обращается к тегам — слои размыты, блок невозможно переиспользовать;
- логика читает тег датчика напрямую — блок не тестируется отдельно от «железа»;
- модуль выхода ещё и читает (`IF "DI_…" THEN "DO_…" := …`) — логика утекла в слой I/O;
- обмен между слоями «пакетом» STRUCT — лишняя связанность и трудная отладка;
- один тег пишут и программа, и внешний клиент — «плавающие» ошибки;
- индикация панели посажена на физический выход — занят выход и потеряна диагностика.

## 9. Циклограммы (правила составления)

Циклограмма — единственный способ показать поведение системы во времени без «железа».
Требования к ней: читаемость человеком и формальная проверяемость агентом.

Где живёт: в документе задания проекта (эталонное место — раздел тест-сценариев).
В этих правилах — только требования; саму диаграмму сюда не копировать, иначе версии
разъедутся.

### 9.1 Геометрия холста (жёстко)

- Блок — строго внутри фенса ```` ```text ````, иначе моноширинность не гарантирована.
- Поле метки строки: имя, дополненное до 16 символов, плюс один пробел = **17 знаков**.
- Ось времени: **60 столбцов** (допустимо 40…80, но одинаково для всех строк блока).
- Строка-сигнал: 17 + 60 = **77 символов**; все строки-сигналы одинаковой длины.
- Строки-связки (только стрелки и `|`) могут быть короче, но без хвостовых пробелов.
- Подписи строк — конкретные имена сигналов проекта; легенда — универсальная (9.9).

### 9.2 Словарь символов (только эти)

| Символ | Значение |
| ------ | -------- |
| `‾` | TRUE — высокий уровень |
| `_` | FALSE — низкий уровень |
| `/` | передний фронт (0→1); новый уровень начинается со **следующего** столбца |
| `\` | задний фронт (1→0); новый уровень начинается со следующего столбца |
| `↓` | стрелка реакции **сверху вниз**, стоит на фронте сигнала-следствия |
| `↑` | стрелка реакции **снизу вверх**, стоит на фронте следствия |
| `\|` | вертикальная причинно-следственная связь по столбцу сигнала |

Запрещено: ASCII-заменители (`-`, `~`, `|` вместо `‾`), «фронты» без смены уровня,
стрелки вне столбца фронта.

### 9.3 Правило столбцов (главный инвариант)

- `+1` столбец = **следующий шаг обработки** по цепочке «вход → логика → выход».
- Сигналы одного шага (например, два выхода, записываемые в одном проходе) меняются
  в одном и том же столбце.
- Инвариант проверки: `столбец(следствие) − столбец(причина) = 1`.
- `1` столбец — условная единица времени. Все шаги выполняются в одном цикле сканирования,
  поэтому столбец ≠ скан: задержек «в 1 цикл» из диаграммы выводить нельзя.

### 9.4 Порядок строк

- По умолчанию причина выше следствия → реакция идёт вниз (`↓`).
- Для цепочки сброса/останова допускается обратный порядок → реакция идёт вверх (`↑` + `|`).
- Типовой порядок: датчик, инициирующий цикл → его производные (нормализация, инверсия
  НЗ/НР) → внутреннее состояние (лэтч, `R_TRIG`, таймер) → выходы → индикация/ЧМИ →
  датчик, завершающий цикл → его производные.

### 9.5 Что обязано быть видно на циклограмме

1. **Самоподхват**: интервал, где причина уже FALSE, а состояние ещё TRUE.
2. **Сброс по фронту**: однократный импульс, а не уровень — видно, что сигнал, оставшийся
   включённым, не блокирует следующий пуск.
3. **Отсутствие самозапуска**: после снятия завершающего сигнала выходы остаются FALSE.
4. **Параллельные выходы** (команда и индикация) — в одном столбце.
5. **Инверсия НЗ/НР датчика** — отдельной строкой (нормализованный сигнал).
6. **Стартовое состояние** (до первого фронта): все линии в исходном уровне, ложных
   импульсов нет.

### 9.6 Процедура построения и проверки (для агента)

1. Составить карту событий: `сигнал → фронт (↑/↓) → шаг обработки (вход / логика / выход)`.
2. Назначить столбцы: первому фронту — 5 (или 0), каждому следующему шагу — `+1`;
   проверить, что параллельные сигналы одного шага получили один столбец.
3. **Строки не рисовать вручную** — генерировать умножением символов, иначе почти
   гарантирован off-by-one:

```powershell
$O  = [string][char]0x203E   # ‾ TRUE
$U  = '_'                    # FALSE
$B  = [string][char]0x5C     # \  задний фронт
$S  = '/'                    # /  передний фронт
$D  = [string][char]0x2193   # ↓  реакция вниз
$Up = [string][char]0x2191   # ↑  реакция вверх
$V  = '|'                    # |  вертикальная связь

# строка-сигнал: поле метки 17 знаков + 60 столбцов
$prefix = 'SignalName'.PadRight(16) + ' '
$row    = $prefix + ($O*5) + $B + ($U*9) + $S + ($O*44)   # 77 знаков
```

4. Записывать блок в документ задания файловой заменой, **не забывая** открывающий
   ```` ```text ```` и закрывающий ```` ``` ````.
5. Проверять скриптом (карта `символ@столбец`, длины строк, инвариант `+1`):

```powershell
$doc   = '<путь к документу задания>'
$lines = [System.IO.File]::ReadAllLines($doc)
# $first, $last — границы блока внутри фенса (0-based)
for ($i = $first; $i -le $last; $i++) {
    $l = $lines[$i]; $m = @()
    for ($c = 0; $c -lt $l.Length; $c++) {
        $ch = $l[$c]
        if ($ch -eq $S -or $ch -eq $B -or $ch -eq $D -or $ch -eq $Up -or $ch -eq $V) {
            $m += ('{0}@{1}' -f $ch, ($c - 17))     # 17 = ширина поля метки
        }
    }
    '{0}: len={1} | {2}' -f ($i + 1), $l.Length, ($m -join ' ')
}
# затем сверить: столбец(следствие) - столбец(причина) = 1
```

6. Только после прохождения проверки — коммит.

### 9.7 Антипаттерны

- стрелка стоит на фронте причины вместо фронта следствия (нарушен `+1`);
- два сигнала одного шага разнесены по столбцам (или последовательные шаги слиты);
- `↑` поставлен на падающий фронт причины, хотя стрелка всегда на фронте следствия;
- вертикальный `|` не совпадает со столбцом сигнала, к которому относится;
- строки-сигналы разной длины → выравнивание разваливается при любой правке;
- ручной набор символов вместо генерации скриптом;
- легенда с именами переменных и блоков проекта → не переносится в другой проект;
- `‾` заменён на `-`, `~`, `≡` — фронт неотличим от плато;
- диаграмма продублирована в правилах: версии разъезжаются (эталон — только в задании).

### 9.8 Чек-лист диаграммы

- [ ] блок внутри ```` ```text ```` и фенс закрыт;
- [ ] все строки-сигналы одинаковой длины (17 + N столбцов);
- [ ] карта `символ@столбец` снята скриптом;
- [ ] инвариант `столбец(следствие) − столбец(причина) = 1` выполняется для всех пар;
- [ ] параллельные сигналы одного шага — в одном столбце;
- [ ] видны самоподхват, сброс по фронту, отсутствие самозапуска;
- [ ] легенда под блоком есть и не содержит имён проекта;
- [ ] после правки других разделов длина блока и столбцы не изменились.

### 9.9 Легенда под блоком (универсальный шаблон)

Формулировка переносится в любой проект **без изменений** — имён переменных, блоков
и модулей в ней быть не должно. Канон:

> Обозначения: `‾` / `_` — уровень сигнала (TRUE / FALSE); `/` и `\` — фронт сигнала,
> новый уровень начинается со следующего столбца; `↓` — стрелка реакции сверху вниз,
> `↑` — снизу вверх, стрелка всегда стоит на фронте сигнала-следствия; `|` — вертикальная
> причинно-следственная связь по столбцу сигнала. **Правило столбцов (универсальное, без
> привязки к именам):** `+1` столбец = следующий шаг обработки по цепочке «вход → логика →
> выход»; сигналы одного шага меняются в одном и том же столбце; проверка корректности
> схемы: столбец фронта-следствия = столбец фронта-причины + 1; все шаги выполняются
> в одном цикле сканирования (OB1), поэтому `1` столбец — условная единица времени,
> а не отдельный скан.

Конкретные имена сигналов — только в подписях строк блока, не в легенде.

## 11. Как поддерживать эти правила

Правила должны оставаться пригодными для **любого** проекта. Поэтому:

- в тексте нет и не должно появляться имён блоков, тегов, адресов, путей и названий
  объектов конкретного проекта — всё это живёт в задании проекта;
- примеры кода — ролевые заглушки, а не «как сделано у нас»;
- при смене технологической задачи файл не правится вообще: меняется только задание;
- файл правится при смене платформы (версия TIA, семейство CPU), языка или соглашений
  команды — и такая правка оформляется как решение с причиной;
- если правило перестало соответствовать платформе, правило исправляется, а не обходится;
- новое правило добавляется, только если оно проверяемо: его можно превратить в пункт
  чек-листа или в команду проверки;
- противоречия между правилами устраняются сразу: два разных ответа на один вопрос хуже,
  чем отсутствие ответа.

Признак того, что файл испорчен: в нём снова появились имена конкретных блоков и тегов
либо раздел «текущее состояние проекта». Состояние проекта живёт в задании и в коде.
