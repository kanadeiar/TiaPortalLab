# TiaPortalLab — standarts

> Инструкции и контекст для AI-ассистента (Cline) при работе с проектом.
> Проект: учебный опытно-экспериментальный проект на ПЛК Siemens S7-1200.
> Среда разработки: **TIA Portal V19** (STEP 7 + WinCC Basic), язык — **SCL** (Structured Control Language, МЭК 61131-3).
> Архитектура: «три слоя без STRUCT» — оркестратор + hardware + логика + HMI, только простые типы.
> Назначение: шаблон правил AI-агента, применимый к любой технологической задаче в этом проекте.

## 0. Инструментарий AI-агента

### Обзор структуры проекта

- Shell — PowerShell (`powershell.exe`), пути в одинарных кавычках.
- `Get-ChildItem -LiteralPath 'd:\_dev\TiaPortalLab' -Recurse -File | Where-Object { $_.FullName -notlike '*\.git\*' }` — обзор всех файлов.
- `read_files` — чтение содержимого файлов.
- `search_codebase` — поиск паттернов по regex.
- Независимые чтения, поиски и команды отправляй **параллельно** в одном ответе — это быстрее, чем последовательно.
- `cmd /c` и сложные пайпы не использовать; `git` запускать с `--no-pager`.

### Что именно лежит в репозитории

| Файл | Что это | Куда попадает в TIA |
| ---- | ------- | ------------------- |
| `*.scl` | внешний источник SCL (External source file) | `PLC → External source files → Generate blocks from source` |
| `*.db` | внешний источник DB (global-DB или instance-DB) | то же |
| `*.udt` | внешний источник PLC data type (UDT) | то же |
| `PLCTags.xml` | экспорт таблицы PLC-тегов | `PLC tags → Import` |
| `README.md` | задание (ТЗ), единственный источник требований | — |
| `.clinerules/standarts.md` | эти правила | — |

**Ключевой факт:** в репозитории **нет** файла проекта `*.ap19` и **нет** конфигурации оборудования.
Проект живёт в GUI TIA Portal; здесь — только исходники, которые в него импортируются. Следствия:

- скомпилировать или запустить проект из терминала нельзя — только `Ctrl+B` в TIA;
- имена блоков и тегов должны совпадать с тем, что реально существует в проекте TIA;
- если правишь `PLCTags.xml`, таблицу нужно импортировать в проект, иначе код не скомпилируется.

### Правила чтения файлов

1. `.clinerules/standarts.md` — правила и контекст.
2. `README.md` — задание и требования (единственный источник истины по задаче).
3. Все `*.scl`, `*.db`, `*.udt`, `PLCTags.xml` — реализация.

### Что агент НЕ делает

- не «собирает» проект из терминала и не создаёт `*.ap19`;
- не переименовывает блоки и теги без согласования (это ломает связь с проектом TIA);
- не тянет сторонние библиотеки — в SCL их нет, есть только стандартные IEC-блоки;
- не пишет код в стиле CoDeSys (см. таблицу в разделе 2).

## 1. Режимы работы (mode)

### codechat — основной код-чат

Обычная помощь с кодом: написание, рефакторинг, отладка.

### reviewer — код-ревью

Проводи детальный код-ревью: ищи баги и антипаттерны, проверяй соответствие стилю, предлагай улучшения с пояснениями.

### architect — архитектор

Проектируй архитектуру: предлагай паттерны и структуру, рисуй диаграммы (Mermaid), сравнивай trade-off'и.

### plc-engineer — инженер по аппаратной части ПЛК

Ищи ошибки в аппаратной части, проверяй исправность на основе описания ПЛК, предлагай улучшения на основании технической документации.
Зона ответственности: конфигурация оборудования в TIA (CPU, модули DI/DQ/AI/AO), карта адресов I/O, схемы подключения, поведение при старте и переходе STOP→RUN, вопросы безопасности.

### st-designer — дизайнер кода на языке SCL

Разработка и анализ кода на SCL: ищи баги и антипаттерны, проверяй соответствие стилю, предлагай улучшения с пояснениями.

## 2. Платформа: TIA Portal

Проект ведётся в TIA Portal V19 для S7-1200. Конструкции CoDeSys в нём либо не существуют, либо не импортируются — использовать их нельзя.

| Понятие | CoDeSys v3 (не использовать) | TIA Portal V19 / S7-1200 (использовать) |
| ------- | ----------------------------- | --------------------------------------- |
| Глобальные переменные | `GVL.Sensor` | таблица PLC-тегов, обращение `"DI_SensorA"` |
| Точка входа | `PROGRAM PLC_PRG` | организационный блок OB1 — в проекте называется `"ProgramCycle"` |
| Циклическая задача | `MAIN_CYCLE` | цикл сканирования OB1 |
| Тело блока | без `BEGIN`/`END_...` | обязательно `BEGIN … END_FUNCTION_BLOCK` |
| Привязка к адресу | `AT %I0.0` в объявлении | адрес в столбце «Адрес» таблицы PLC-тегов |
| Обращение к локальной | `Start` | `#Start` |
| Обращение к глобальной | `GVL.Start` | `"Tag_Name"` или `"Global_DB".Start` |
| Вложенный FB | `fb1 : FB_Name;` | `#fb1 : "FB_Name";` (multi-instance внутри FB) |
| Экземплярный DB | — | `"ConveyorMain_DB"` (single instance), вызов `"ConveyorMain_DB"();` |
| Ретентивность | `VAR_GLOBAL RETAIN` | retentive-память CPU / `RETAIN` в DB; PLC-теги не retentive |
| Пользовательский тип | `TYPE ... STRUCT` | `TYPE "Udt_Name" ... END_TYPE` (PLC data type) |
| Расширение исходника | `*.st` | `*.scl` (+ `*.db`, `*.udt`) |
| Сборка | Build → Generate Code | `Ctrl+B` (Compile → Software (rebuild all)) |
| Симуляция | — | PLCSIM V19 (в TIA — «Start simulation») |
| Онлайн-отладка | Force (F7), Write (Ctrl+F7) | мониторинг + Watch table: `Modify now` и `Force job` |

Дополнительно про S7-1200:

- блоки по умолчанию **оптимизированные** (`S7_Optimized_Access := 'TRUE'`) — доступ к полям DB только по именам, абсолютных смещений нет;
- в S7-1200 нет `VAR_GLOBAL`, нет `GVL`, нет `MAIN_CYCLE`: глобальные данные — это PLC-теги и DB;
- таймеры, счётчики и IEC-блоки требуют экземпляр (multi-instance в `VAR` или отдельный instance-DB) и должны вызываться **каждый цикл**;
- «Force» в TIA — это force job: снимается через `Force → Delete all force jobs` либо переводом CPU в STOP;
- `VAR_TEMP` между вызовами не сохраняются; состояние живёт в статических `VAR` (instance-DB).

## 3. Стиль кода и соглашения (SCL)

### Общие правила

- Пиши код на **SCL** для TIA Portal V19 по стандарту МЭК 61131-3.
- Используй стандартные инструкции и стандартные IEC-блоки (`TON`, `TOF`, `TP`, `CTU`, `CTD`, `CTUD`, `R_TRIG`, `F_TRIG`).
- Локальные обращения внутри блока — всегда с `#`, глобальные — в кавычках: `#BoxOnStart`, `"DI_SensorA"`, `"Hmi_DB".LampWork`.
- Никаких «магических чисел»: уставки и задержки — в `VAR CONSTANT` (`TIME#5S`, `INT#10` и т.п.).
- Промежуточные переменные создавай только если они улучшают читаемость.
- Комментарии `//` — только для неочевидной логики; назначение блока — в комментарии под его заголовком.
- Отступ — 4 пробела, табы не использовать; строки из одних пробелов не оставлять.
- Кириллица допустима в комментариях и описаниях, **никогда** в идентификаторах.
- Длинную логику группируй через `REGION … END_REGION`.

### Именование

- Локальные и статические переменные — с маленькой буквы (`boxOnStart`, `rtBoxOnEnd`).
- Входы/выходы FB, глобальные теги и блоки — с большой буквы (`BoxOnStart`, `DI_SensorA`, `ConveyorMain`).
- Имя файла исходника = имя блока: `ConveyorMain.scl` содержит `FUNCTION_BLOCK "ConveyorMain"`.

| Постфикс | Тип | Пример |
| -------- | --- | ------ |
| `_DB` | Data block | `ConveyorMain_DB`, `Hmi_DB` |
| `_InOut` | Таблица PLC-тегов | `Tags_InOut` |
| — | Function block | `ConveyorMain` |
| — | Function | `AlwaysOn` |
| — | Организационный блок | `ProgramCycle` (OB1) |

| Префикс | Тип сигнала | Пример |
| ------- | ----------- | ------ |
| `DI_` | дискретный вход | `DI_SensorA` |
| `DO_` | дискретный выход | `DO_ComMotor` |
| `AI_` / `AO_` | аналоговый вход/выход | `AI_Level` |
| `HMI_` | сигнал для панели оператора (без физического адреса) | `HMI_LampWork` |
| `Cmd_` / `Sts_` | команда / статус | `CmdStart`, `StsRunning` |

> Имена в SCL нечувствительны к регистру, но пишутся ровно так, как в таблице тегов и в проекте TIA.
> Для нового проекта принимаем префиксы тегов в верхнем регистре (`DI_`, `DO_`, `HMI_`), имена блоков и DB — CamelCase (`ConveyorMain`, `ConveyorMain_DB`).

### Порядок секций в FB (TIA SCL)

1. `VAR_INPUT` — входы
2. `VAR_OUTPUT` — выходы
3. `VAR_IN_OUT` — параметры по ссылке
4. `VAR` — статические (живут в instance-DB): таймеры, счётчики, вложенные FB
5. `VAR_TEMP` — временные
6. `VAR CONSTANT` — константы

Тело — после `BEGIN`, блок закрывается `END_FUNCTION_BLOCK` / `END_FUNCTION` / `END_ORGANIZATION_BLOCK`.

Эталон объявления:

```scl
FUNCTION_BLOCK "ConveyorMain"
{ S7_Optimized_Access := 'TRUE' }
VERSION : 0.1
   VAR_INPUT
      BoxOnStart : Bool;
   END_VAR
   VAR_OUTPUT
      ComRotate : Bool;
   END_VAR
   VAR
      rtBoxOnEnd : R_TRIG;
   END_VAR

BEGIN
    // логика
END_FUNCTION_BLOCK
```

### Правила Function Block

- **Вызывать каждый цикл и безусловно** — таймеры, счётчики и edge-детекторы хранят состояние в экземпляре.
- **Не мутировать `VAR_INPUT`** — работать с локальной копией.
- **Инициализировать статические `VAR`**: `state : Int := 0;`.
- **RETAIN осознанно**: уставки и счётчики — да; состояние RS-триггера и команды двигателя — нет (безопасный старт после STOP→RUN).
- **Выходные параметры FB записывай через `=>`** в вызове: `#logic(BoxOnEnd := #boxOnEnd, ComRotate => #comRotate);`.
- Вложенные FB объявляй в `VAR` (multi-instance); отдельный instance-DB нужен только для блоков, вызываемых из OB или из нескольких мест.
- Один блок — одна ответственность; блок не длиннее ~200 строк, иначе дели.

### Правила работы с тегами (вместо GVL)

- Все физические I/O — только в таблице PLC-тегов, с абсолютным адресом и осмысленным именем.
- Из кода — только символические имена. Прямая адресация (`%I0.0`, `%Q0.0`) в логике — антипаттерн.
- Абсолютные адреса должны совпадать с конфигурацией оборудования; при добавлении модулей карту адресов обновлять и в TIA, и в `PLCTags.xml`, и в `README.md`.
- Лампы и кнопки, существующие только на панели оператора, не сажаются на физический `%Q` — это поля DB (`"Hmi_DB".LampWork`) или теги `HMI_*` без адреса.
- Изменение `PLCTags.xml` = изменение проекта: после правки файла таблицу нужно импортировать в TIA и перекомпилировать.

#### Доступ из Factory I/O (обязательно)

Поле имитируется средой **Factory I/O**: она записывает значения датчиков и читает команды, то есть работает и как датчик, и как панель. Поэтому у **всех** тегов I/O права доступа должны быть открыты:

| Атрибут тега | Значение | Зачем |
| ------------ | -------- | ----- |
| `hmiVisible` | `True` | тег виден внешнему клиенту (Factory I/O, HMI, OPC UA) |
| `hmiAccessible` | `True` | тег доступен для чтения извне |
| `hmiWriteable` | `True` | тег доступен для записи извне (Factory I/O пишет датчики) |

В XML это выглядит так — ровно так, как в `PLCTags.xml`, занижать эти атрибуты нельзя:

```xml
<Tag type='Bool' hmiVisible='True' hmiWriteable='True' hmiAccessible='True' addr='%I0.0'>DI_SensorA</Tag>
```

Следствия, которые нельзя нарушать:

- **`DI_*` пишет только Factory I/O**, программа эти теги только читает (через `HardwareInput`): присваивание `"DI_SensorA" := …` в коде запрещено.
- **`DO_*` пишет только программа** (через `HardwareOutput`), Factory I/O читает их и приводит в действие механизмы.
- Внутренние данные (состояние триггера, счётчики, лампы панели) храним в DB (`"Hmi_DB"`, instance-DB), а не в I/O-тегах.
- Двойная запись в один тег (программой и внешней средой) — источник «плавающих» ошибок; если тег пишется извне, программа в него не пишет.

#### Подключение Factory I/O к S7-1200

- **Драйвер «Siemens S7-1200/1500» (S7 / PUT-GET)**: у CPU включить `Properties → Protection & Security → Connection mechanisms → Permit access with PUT/GET communication from remote partner`. В Factory I/O сигналы привязываются к **абсолютным адресам** (`I0.0`, `I0.1`, `Q0.0`, `Q0.1`) — при изменении карты адресов синхронно править конфигурацию Factory I/O.
- **Драйвер OPC UA**: у CPU включить `OPC UA → Server` (S7-1200 FW ≥ 4.4) и оставить у тегов `hmiVisible`/`hmiAccessible`/`hmiWriteable = True`; в клиенте теги доступны по именам.
- **PLCSIM**: драйвер Factory I/O подключается к виртуальному CPU, требования к тегам те же.
- Атрибуты `hmi*` действуют для HMI и OPC UA; при доступе по S7/PUT-GET решает настройка CPU, а не атрибут тега.

## 4. Стандартные IEC-блоки — когда использовать

Все они требуют экземпляр и вызываются **каждый цикл** (безусловно).

### Таймеры

| FB | Когда использовать | В SCL |
| -- | ------------------ | ------ |
| `TON` | задержка старта, антидребезг, контроль времени | `#tonStart(IN := #start, PT := TIME#2S);` → `#tonStart.Q` |
| `TOF` | задержка стопа, удержание аварии | `#tofAlarm(IN := #fault, PT := TIME#10S);` |
| `TP` | импульс фиксации, формирование сигнала заданной длины | `#tpPulse(IN := #trig, PT := TIME#500MS);` |
| `TONR` | накопление времени (S7-1200 поддерживает) | — |

### Счётчики

| FB | Когда использовать |
| -- | ------------------ |
| `CTU` | счётчик деталей, циклов |
| `CTD` | обратный отсчёт |
| `CTUD` | балансировка, контроль уровня |

### Edge-детекторы

| FB | Когда использовать |
| -- | ------------------ |
| `R_TRIG` | нажатие кнопки, начало события (передний фронт) |
| `F_TRIG` | отпускание, конец события (задний фронт) |

### Бистабильные элементы

| Функция | Когда использовать |
| ------- | ------------------ |
| `SR` | доминирует установка (`SR` — инструкция LAD/FBD в TIA) |
| `RS` | доминирует сброс, безопаснее для команды «стоп» |

> В SCL бистабильный элемент пишется выражением с самоподхватом — так приоритет сброса виден в коде:
> `#out := (#set OR #out) AND NOT #reset;`
> Не используй самоподхват по уровню там, где нужен учёт фронта: коробка, стоящая на датчике, будет постоянно сбрасывать триггер (см. `R_TRIG` и раздел 9).

## 5. Архитектурные паттерны

### State Machine (машина состояний)

- `CASE #state OF` для переходов; состояние — статическая `VAR` с инициализацией (`state : Int := 0;`).
- Явно обрабатывать состояния `Idle`/`Run`/`Fault`/`Reset`.
- Выходы выставлять в каждом состоянии (не «забывать»), либо в конце блока один раз — по состоянию.
- Переходы только по событиям (фронты, условия), без «прыжков» через несколько состояний.

### Главный блок программы (порядок вызовов)

1. Чтение входов (HardwareInput)
2. Технологическая логика (LogicDevice)
3. Запись выходов (HardwareOutput)
4. Режим работы
5. Обработка ошибок и безопасности
6. Обмен с панелью оператора (HMIInterface)

`ProgramCycle` (OB1) — только вызов оркестратора `"ConveyorMain_DB"();` и ничего больше.

### Паттерн FB_ErrorHandler

- Использовать, когда по заданию требуется обработка ошибок.
- `VAR_OUTPUT ErrorCode : Int` (0 — нет ошибки), `ErrorActive : Bool`.
- Диагностика по таймауту (`TON`) и по противоречивым сигнатурам датчиков.
- Квитирование ошибки — отдельный вход `Reset` (фронт), а не самосброс.

## 6. Цикловое выполнение

### Правила цикла

- OB1 (`ProgramCycle`) выполняется циклически сам — вызывать его вручную не нужно.
- Все FB вызывать каждый MAIN-цикл (то есть каждый вызов OB1), в том числе таймеры и счётчики.
- Не блокировать цикл: никаких `WHILE TRUE`, длинных `FOR`, ожиданий.
- Состояние — в статических переменных (instance-DB), не в `VAR_TEMP`.
- Не полагаться на порядок вызовов внутри OB, кроме явно заданного оркестратором.

### Антипаттерны (не делать)

- Прямая адресация в логике: `IF "DI_SensorA" = FALSE ...` — ок, а `IF %I0.0 = FALSE ...` — нет.
- Вызов таймера по условию: `IF #start THEN #tonT(IN := TRUE, PT := ...); END_IF;` — при неактивном условии таймер не вызывается, его `Q` и `ET` «замерзают».
- Вызов FB без экземпляра / без instance-DB.
- Мутация входных параметров: `#Speed := #Speed * 0.5;`.
- `WHILE TRUE` вместо циклического OB.
- Хранение рабочего состояния в `VAR_TEMP` или в M-битах вместо instance-DB.
- `GOTO` и «лапша» из вложенных `IF` глубже 3 уровней — используй `CASE #state OF`.
- Глобальные «флаги-костыли» в PLC-тегах для обмена между блоками: обмен — через `VAR_INPUT`/`VAR_OUTPUT`.

### Паттерны (делать)

- Символическая адресация через таблицу PLC-тегов.
- Экземпляр для каждого FB: `#logic : "LogicDevice";` + вызов `#logic(...);`.
- Локальная копия для расчётов: `#localSpeed := #Speed * 0.5;`.
- Таймер вызывается каждый цикл: `#tonStart(IN := #start, PT := TIME#5S);`.
- Явный комментарий у неочевидной логики и `REGION` для группировки.

## 7. Язык SCL — справочник

### Синтаксис

- Ключевые слова: `ORGANIZATION_BLOCK`, `FUNCTION_BLOCK`, `FUNCTION`, `DATA_BLOCK`, `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT`, `VAR_TEMP`, `VAR`, `END_VAR`, `BEGIN`, `END_...`
- Комментарии: `// однострочный` и `(* многострочный *)`
- Разделитель инструкций: `;` (точка с запятой обязательна)
- Присваивание: `:=` (не `=`); сравнение: `=`, `<>`, `<`, `>`, `<=`, `>=`
- Логические: `AND`, `OR`, `NOT`, `XOR`; арифметика: `+`, `-`, `*`, `/`, `MOD`
- Константы: `TRUE`, `FALSE`; литералы — `16#FF`, `2#1010_1010`, `1.5`, `INT#10`, `TIME#5S`, `T#1H30M`
- Регистр не важен, но имена блоков/тегов пишутся как в проекте

### Базовые типы данных (TIA Portal)

| Тип | Диапазон | Размер |
| --- | -------- | ------ |
| `Bool` | TRUE/FALSE | 1 бит |
| `Byte` | 0..255 | 8 бит |
| `Word` | 0..65535 | 16 бит |
| `DWord` | 0..4294967295 | 32 бита |
| `SInt` | -128..127 | 8 бит |
| `Int` | -32768..32767 | 16 бит |
| `DInt` | -2^31..2^31-1 | 32 бита |
| `USInt` / `UInt` / `UDInt` | 0..255 / 0..65535 / 0..4294967295 | 8 / 16 / 32 бита |
| `Real` | ±3.4E±38 | 32 бита (IEEE 754) |
| `LReal` | ±1.7E±308 | 64 бита |
| `Time` | `TIME#…` | 32 бита (мс) |
| `Char` / `String` | 1 символ / до 254 символов | — |
| `DTL` | дата и время | 12 байт |

Приведение типов — явное: `INT_TO_REAL()`, `REAL_TO_INT()`, `ROUND()`, `TRUNC()`, `TIME_TO_DINT()`.

### Обращение к данным

| Что | Синтаксис | Пример |
| --- | --------- | ------ |
| Локальная переменная блока | `#name` | `#boxOnStart := TRUE;` |
| Вход/выход FB | `#name` | `#ComRotate := FALSE;` |
| PLC-тег | `"TagName"` | `"DO_ComMotor" := #cmdRotate;` |
| Поле global-DB | `"DbName".Field` | `"Hmi_DB".LampWork := #beltRun;` |
| Поле структуры в DB | `"DbName".Struct.Field` | `"Cfg_DB".Motor.Speed := 1.5;` |
| Экземпляр вложенного FB | `#instance.Output` | `#logic.ComRotate` |
| Меркер (только при необходимости) | `"M_Flag"` или `%M10.0` | `"M_Reset" := TRUE;` |

Правило: `#` — только для локального/статического, кавычки — только для глобального.

### Вызов блоков

```scl
// FB с single-instance DB (обычно из OB1)
"ConveyorMain_DB"();

// Вложенный FB (multi-instance) — объявлен в VAR
#hardIn();
#logic(BoxOnStart := #hardIn.BoxOnStart,
       BoxOnEnd   := #hardIn.BoxOnEnd);
#hardOut(ComRotate := #logic.ComRotate);
#hmi(BeltRun := #logic.ComRotate);

// Выход через =>
#logic(BoxOnEnd := #boxOnEnd, ComRotate => #comRotate);

// FC
#alwaysOn();

// Стандартный IEC-блок
#tonStart(IN := #cmdRun, PT := TIME#2S);
#rtBoxOnEnd(CLK := #boxOnEnd);
#ctuBoxes(CU := #rtBoxOnEnd.Q, R := #reset, PV := 100);
```

### Управляющие конструкции

```scl
// Ветвление
IF #a AND NOT #b THEN
    #out := TRUE;
ELSIF #a THEN
    #out := FALSE;
ELSE
    #out := FALSE;
END_IF;

// Машина состояний
CASE #state OF
    0:  // Idle
        IF #boxOnStart THEN
            #state := 10;
        END_IF;
    10: // Run
        IF #boxOnEnd THEN
            #state := 20;
        END_IF;
    20: // Stopped / Wait
        IF NOT #boxOnEnd THEN
            #state := 0;
        END_IF;
ELSE
    #state := 0;
END_CASE;

// Цикл
FOR #i := 0 TO 7 DO
    #sum := #sum + #arr[#i];
END_FOR;

// Группировка
REGION Inputs
    #hardIn();
END_REGION
```

### Частые ошибки компиляции в TIA

| Сообщение / симптом | Причина |
| ------------------- | ------- |
| «Не удаётся найти тег …» | тега нет в таблице тегов или имя в коде не совпадает |
| «Адрес %I0.0 не существует» | нет конфигурации оборудования/модуля с таким адресом |
| «Тип … неизвестен» | не сгенерирован FB/UDT, от которого зависит блок (порядок импорта) |
| «Экземпляр не объявлен» | FB вызван без экземпляра или без `#` |
| «Недопустимая запись в константу/вход» | попытка присвоить `VAR_INPUT` или `VAR CONSTANT` |
| «Отсутствует `END_...`» | потерян `BEGIN`/`END_FUNCTION_BLOCK` при правке исходника |

## 8. Шаблон архитектуры проекта (три слоя)

> **Образец, а не точная реализация.** Точная реализация и задание — в `README.md`.

Проект строится по схеме: **чистый оркестратор + hardware (вход) + hardware (выход) + логика + HMI**.

```
TiaPortalLab/
├── ProgramCycle.scl           ← OB1: циклический вызов оркестратора
├── PLCTags.xml                ← таблица PLC-тегов (замена GVL)
├── ConveyorObject/            ← ядро технологического приложения
│   ├── ConveyorMain.scl       ← чистый оркестратор (без обращений к тегам)
│   ├── ConveyorMain_DB.db     ← single-instance DB оркестратора
│   ├── HardwareInput.scl      ← чтение датчиков (только вход)
│   ├── HardwareOutput.scl     ← запись команд (только выход)
│   ├── Logic/LogicDevice.scl  ← чистая логика управления (RS-триггер, ПИД и т.д.)
│   └── HMIInterface.scl       ← сопряжение с панелью оператора
└── README.md
```

### Принципы

1. **Нет STRUCT-посредников** — данные передаются простыми типами (`Bool`, `Int`, `Time`) через `VAR_INPUT`/`VAR_OUTPUT` FB. UDT допустим только для конфигурации и уставок, но не как «пакет» для передачи данных между слоями.
2. **Оркестратор — чистый** — в `ConveyorMain` нет ни одного обращения к PLC-тегам и DB, только соединение блоков.
3. **HardwareInput** — только читает теги датчиков, ничего не пишет.
4. **HardwareOutput** — только пишет в теги выходов, ничего не читает.
5. **LogicDevice** — чистая логика: не знает про теги, датчики и механизмы.
6. **HMIInterface** — только пишет в DB панели (`"Hmi_DB"`) и читает кнопки панели.
7. **Легко портируется** — при смене ПЛК меняются только `HardwareInput`, `HardwareOutput`, `HMIInterface` и конфигурация оборудования.

### Шаблон назначения блоков

| Блок | Ответственность |
| ---- | --------------- |
| `ProgramCycle` (OB1) | точка входа, циклический вызов оркестратора |
| `ConveyorMain` | чистый оркестратор: HardwareInput → LogicDevice → HardwareOutput → HMIInterface |
| `HardwareInput` | чтение полевых датчиков из PLC-тегов (нормализация НЗ/НР) |
| `HardwareOutput` | запись команд в PLC-теги |
| `LogicDevice` | алгоритмы и технологическая логика |
| `HMIInterface` | лампы/кнопки панели оператора |
| `PLCTags.xml` | глобальные переменные с привязкой к физическим входам/выходам |
| `Hmi_DB` | данные только для панели оператора (без адресов I/O) |

### Порядок импорта в TIA (важно)

`UDT` → `FB` (логика и hardware) → `ConveyorMain` → global-DB (`Hmi_DB`) → single-instance DB (`ConveyorMain_DB`) → OB (`ProgramCycle`) → таблица тегов.
Если порядок нарушен, TIA выдаст «тип не найден».

      BoxOnStart : Bool;
      BoxOnEnd   : Bool;

## 10. Циклограммы (правила составления)

Циклограмма — единственный способ показать поведение системы во времени без железа. Требования к ней: **читаемость человеком** и **формальная проверяемость агентом**.

Где живёт: эталонная циклограмма проекта — в `README.md` (в разделе тест-сценариев). В этих правилах — только требования к ней; саму диаграмму в правила не копировать, чтобы версии не разъезжались.

### 10.1 Геометрия холста (жёстко)

- Блок — строго внутри фенса ```` ```text ```` (иначе моноширинность не гарантирована и столбцы поедут).
- Поле метки строки: имя, дополненное до 16 символов, плюс один пробел = **17 знаков**.
- Ось времени: **60 столбцов** (допустимо 40…80, но одинаково для всех строк блока).
- Строка-сигнал: 17 + 60 = **77 символов**; все строки-сигналы обязаны быть одинаковой длины.
- Строки-связки (только стрелки/`|`) могут быть короче, но без «хвостовых» пробелов.
- Подписи строк в блоке — конкретные имена сигналов проекта; легенда — универсальная (см. 10.9).

### 10.2 Словарь символов (только эти)

| Символ | Значение |
| ------ | -------- |
| `‾` | TRUE — высокий уровень |
| `_` | FALSE — низкий уровень |
| `/` | передний фронт (0→1); новый уровень начинается со **следующего** столбца |
| `\` | задний фронт (1→0); новый уровень начинается со **следующего** столбца |
| `↓` | стрелка реакции **сверху вниз**; стоит на фронте сигнала-следствия |
| `↑` | стрелка реакции **снизу вверх**; стоит на фронте сигнала-следствия |
| `\|` | вертикальная причинно-следственная связь по столбцу сигнала |

Запрещено: ASCII-заменители (`-`, `~`, `|` вместо `‾`), «фронты» без смены уровня, стрелки вне столбца фронта.

### 10.3 Правило столбцов (главный инвариант)

- `+1` столбец = **следующий шаг обработки** по цепочке «вход → логика → выход».
- Сигналы **одного шага** (например, два выхода, записываемые в одном проходе) меняются **в одном столбце**.
- Инвариант для проверки: `столбец(следствие) − столбец(причина) = 1`.
- `1` столбец — **условная** единица времени. Все шаги выполняются в одном цикле сканирования (OB1), поэтому столбец ≠ скан: никаких задержек «в 1 цикл» из диаграммы выводить нельзя.

### 10.4 Порядок строк

- По умолчанию причина выше следствия → реакция идёт вниз (`↓`).
- Для цепочки сброса/останова допускается обратный порядок (завершающий датчик ниже выходов) → реакция идёт вверх (`↑` + `|`).
- Типовой порядок сверху вниз: датчик, инициирующий цикл → его производные (нормализация, инверсия НЗ/НР) → внутреннее состояние (лэтч, `R_TRIG`, таймер) → выходы → индикация/ЧМИ → датчик, завершающий цикл → его производные.

### 10.5 Что обязано быть видно на циклограмме

1. **Самоподхват**: интервал, где причина уже FALSE, а состояние ещё TRUE.
2. **Сброс по фронту**: однократный импульс (фронт), а не уровень — видно, что сигнал, оставшийся включённым, не блокирует следующий пуск.
3. **Отсутствие самозапуска**: после снятия завершающего сигнала выходы остаются FALSE.
4. **Параллельные выходы** (команда + индикация) — в одном столбце.
5. **Инверсия НЗ/НР датчика** — отдельной строкой (нормализованный сигнал), чтобы фронт в логике был виден явно.
6. **Стартовое состояние** (до первого фронта): все линии в исходном уровне, ложных импульсов нет.

### 10.6 Процедура построения и проверки (для агента)

1. Составить карту событий: `сигнал → фронт (↑/↓) → шаг обработки (вход / логика / выход)`.
2. Назначить столбцы: первому фронту — 5 (или 0), каждому следующему шагу — `+1`. Проверить, что параллельные сигналы одного шага получили один столбец.
3. **Строки не рисовать вручную.** Генерировать умножением символов, иначе почти гарантирован off-by-one:

```powershell
$O  = [string][char]0x203E   # ‾ TRUE
$U  = '_'                    # FALSE
$B  = [string][char]0x5C     # \  задний фронт
$S  = '/'                    # /  передний фронт
$D  = [string][char]0x2193   # ↓  реакция вниз
$Up = [string][char]0x2191   # ↑  реакция вверх
$V  = '|'                    # |  вертикальная связь

# строка-сигнал: поле метки 17 знаков + 60 столбцов
$prefix = 'SignalName'.PadRight(16) + ' '
$row    = $prefix + ($O*5) + $B + ($U*9) + $S + ($O*44)   # 77 знаков
```

4. Записывать блок в `README.md` файловой заменой, **не забывая** открывающий ```` ```text ```` и закрывающий ```` ``` ````.
5. Проверять скриптом (карта `символ@столбец` + длины + инвариант `+1`):

```powershell
$lines = [System.IO.File]::ReadAllLines('README.md')
# $first, $last — границы блока внутри фенса (номера строк, 0-based)
for ($i = $first; $i -le $last; $i++) {
    $l = $lines[$i]; $m = @()
    for ($c = 0; $c -lt $l.Length; $c++) {
        $ch = $l[$c]
        if ($ch -eq $S -or $ch -eq $B -or $ch -eq $D -or $ch -eq $Up -or $ch -eq $V) {
            $m += ('{0}@{1}' -f $ch, ($c - 17))     # 17 = ширина поля метки
        }
    }
    '{0}: len={1} | {2}' -f ($i + 1), $l.Length, ($m -join ' ')
}
# затем глазами/скриптом сверить: столбец(следствие) - столбец(причина) = 1
```

6. Только после прохождения проверки — коммит.

### 10.7 Антипаттерны

- Стрелка стоит на фронте **причины** вместо фронта следствия (нарушен `+1`).
- Два сигнала одного шага разнесены по разным столбцам (или наоборот: последовательные шаги слиты в один столбец).
- `↑` поставлен на падающий фронт причины, хотя по легенде стрелка всегда стоит на фронте следствия.
- Вертикальный `|` не совпадает со столбцом сигнала, к которому относится (визуально «висит в воздухе»).
- Строки-сигналы разной длины → при любой правке выравнивание разваливается.
- Ручной набор символов вместо генерации скриптом (off-by-one почти неизбежен).
- Легенда с именами переменных/блоков проекта → не переносится в другой проект.
- `‾` заменён на `-`, `~`, `≡`: теряется понятие уровня, фронт неотличим от плато.
- Диаграмма продублирована в правилах: через месяц версии разъезжаются (эталон — только в `README.md`).

### 10.8 Чек-лист диаграммы

- [ ] блок внутри ```` ```text ```` и фенс закрыт;
- [ ] все строки-сигналы одинаковой длины (17 + N столбцов);
- [ ] карта `символ@столбец` снята скриптом;
- [ ] инвариант `столбец(следствие) − столбец(причина) = 1` выполняется для всех пар;
- [ ] параллельные сигналы одного шага — в одном столбце;
- [ ] видны самоподхват, сброс по фронту, отсутствие самозапуска;
- [ ] легенда под блоком есть и не содержит имён проекта;
- [ ] после правки других разделов столбцы и длина блока не изменились (перепроверить скриптом).

### 10.9 Легенда под блоком (универсальный шаблон)

Формулировка переносится в любой проект **без изменений** — имён переменных, блоков и модулей в ней быть не должно. Канон:

> Обозначения: `‾` / `_` — уровень сигнала (TRUE / FALSE); `/` и `\` — фронт сигнала, новый уровень начинается со следующего столбца; `↓` — стрелка реакции сверху вниз, `↑` — снизу вверх, стрелка всегда стоит на фронте сигнала-следствия; `|` — вертикальная причинно-следственная связь по столбцу сигнала. **Правило столбцов (универсальное, без привязки к именам):** `+1` столбец = следующий шаг обработки по цепочке «вход → логика → выход»; сигналы одного шага меняются в одном и том же столбце; проверка корректности схемы: столбец фронта-следствия = столбец фронта-причины + 1; все шаги выполняются в одном цикле сканирования (OB1), поэтому `1` столбец — условная единица времени, а не отдельный скан.

Конкретные имена сигналов — только в подписях строк самого блока, не в легенде.
