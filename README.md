# TiaPortalLab

Лаборатория опытно-экспериментальных технологических приложений на Siemens TIA Portal V19.

## Задание: накопление коробок на буферном конвейере и выдача партиями по 3 шт.

## 1. Цель

Предыдущая задача (один конвейер: пуск по датчику начала ленты, останов по датчику конца)
выполнена и осталась в истории git. Это задание — следующий уровень: два конвейера,
накопление, партия, подсчёт коробок и ожидание одного механизма, пока другой выполняет работу.

Требуется разработать программу для ПЛК, которая:

1. принимает коробки приёмным конвейером и передаёт их на буферный;
2. накапливает на буферном конвейере партию из 3 коробок;
3. выдаёт накопленную партию с линии, прекращая приём коробок на время выдачи;
4. после выдачи автоматически начинает набор следующей партии;
5. считает коробки: сколько коробок находится на буфере и сколько выгружено всего;
6. показывает состояние линии на панели оператора.

Что тренируется в этой задаче (по сравнению с предыдущей):

- межмеханизмные блокировки: передача коробки из зоны в зону и запрет подачи в занятую зону;
- машина состояний (`Idle` → `Fill` → `Discharge`) с явными переходами и безопасной ветвью `ELSE`;
- счётчики и одноразовые импульсы (`R_TRIG`) вместо сигналов «по уровню», которые залипают;
- нормально закрытые датчики: инверсия выполняется в одном слое (`HardwareInput`), логика работает
  с положительной логикой «коробка есть»;
- подтверждение события по выдержке времени (`TON`) и корректный сброс таймера при выходе из состояния;
- слоистая архитектура: OB1 → оркестратор → вход / логика / выход / ЧМИ;
- циклограммы и тест-сценарии как часть задания, а не «потом».

## 3. Описание объекта управления

### 3.1 Состав линии

```text
коробки ──▶ лента 1 ──▶ P1 ──▶ P2 ──▶ P3 ──▶ выдача партии
              ▲         ▲                  ▲
              S1        S2                 S3
```

| Объект | Обозначение | Описание |
| ------ | ----------- | -------- |
| Подача коробок | — | коробки подаются на приёмную ленту поштучно (оператор или подающее устройство) |
| Приёмный конвейер | лента 1 | перевозит коробку из зоны подачи в зону загрузки буфера |
| Буферный конвейер | лента 2 | накапливает коробки (позиции P1…P3) и выдаёт партию за правую границу |
| Зона загрузки | P1 | участок буферной ленты под датчиком S2 |
| Зона выгрузки | P3 | участок у правой границы; за ним коробка покидает линию |
| Партия | `BATCH_SIZE = 3` | коробки, которые буфер накапливает и выдаёт одной пачкой |

### 3.2 Датчики и приводы

Датчики нормально закрытые (НЗ / NC): сигнал на входе ПЛК равен `0`, когда коробка есть.
В логике используется положительная логика «коробка есть» = `TRUE` (инверсия в `HardwareInput`).

| Датчик | Тег | Где стоит | «Коробка есть» в логике |
| ------ | --- | --------- | ----------------------- |
| S1 | `DI_SensorItemReady` | начало приёмной ленты | `ItemReady = TRUE` |
| S2 | `DI_SensorAtEntry` | начало буферной ленты (P1) | `AtEntry = TRUE` |
| S3 | `DI_SensorAtExit` | конец буферной ленты (за P3) | `AtExit = TRUE` |

| Привод | Тег | Механизм |
| ------ | --- | -------- |
| лента 1 | `DO_CommandEntryConveyer` | двигатель приёмного конвейера |
| лента 2 | `DO_CommandBufferConveyer` | двигатель буферного конвейера |

Адреса и типы — в `PLCTags.xml`; в коде абсолютных адресов нет, только символьные имена.

### 3.3 Технологический цикл

1. Коробка подаётся на приёмную ленту и попадает в датчик S1.
2. Лента 1 включается и везёт коробку к буферу. После схода коробки с S1 лента **не
   останавливается** (самоподхват): коробка должна доехать до зоны загрузки, а не встать посередине.
3. Коробка доходит до S2 → лента 1 не останавливается, лента 2 включается и вместе они перетаскивают коробку
   из ленты 1 на ленту 2. 
4. Коробка покидает S2 → Коробка считается: `BufferCount += 1`. Как только коробка сходит с S2, лента 2 останавливается: следующая коробка может войти в зону загрузки, а накопленные коробки остаются на своих позициях.
5. Пункты 1–4 повторяются. Каждая новая коробка сдвигает очередь на одну позицию: P1 → P2 → P3.
6. Когда на буфере набрано `BATCH_SIZE` коробок, набор прекращается: лента 1 больше не включается
   (коробка на S1, если она есть, ждёт), лента 2 работает непрерывно и свозит партию за правую границу.
7. По S3 происходит подсчет выгруженных коробок: `BufferCount -= 1`, затемк когда все коробки будут выгружены - `BufferCount := 0`.
8. Линия возвращается в ожидание. Коробка, стоящая на приёмной ленте, принимается в новую партию
   автоматически — набор начинается без участия оператора.

## 4. Уровни сигналов датчиков (НЗ / NC)

Датчики нормально закрытые, поэтому в программе их сигналы **инвертируются** (слой `HardwareInput`):

| Состояние | Сигнал на входе ПЛК | «Коробка обнаружена» в логике |
| --------- | ------------------- | ----------------------------- |
| коробки нет | `1` (TRUE) | FALSE |
| коробка есть | `0` (FALSE) | TRUE |
| обрыв провода / нет питания | `0` (FALSE) | TRUE — неотличимо от коробки, учитывать при диагностике |

## 5. Требования к программе на ПЛК

### 5.1 Постоянные

| Константа | Значение | Смысл |
| --------- | -------- | ----- |
| `BATCH_SIZE` | `3` | коробок в партии |

### 5.4 Счёт коробок

1. `BufferCount` увеличивается на единицу по **заднему фронту** `AtEntry`.
2. `BufferCount` уменьшается во время выгрузки: пока партия едет, панель показывает, сколько
   коробок было в партии.
3. Признак полной партии: `BatchReady := BufferCount >= BATCH_SIZE`.
4. Импульс окончания выгрузки: `BatchDone := EmptyTimer.Q` (один скан). По нему выполняется
   `Count := Count + BufferCount; BufferCount := 0`.
5. Типы: `BufferCount`, `Count` — `Int`; в ЧМИ передаются без преобразований.
6. `R_TRIG` и `TON` вызываются безусловно каждый цикл (не внутри `IF` и не внутри `CASE`).

## 6. Требования к интерфейсу оператора (ЧМИ)

Обмен с панелью — только через поля global-DB `Hmi_DB` (единственный канал). Блок `HMIInterface`
пишет эти поля из данных логики.

| Поле `"Hmi_DB"` | Тип | Смысл |
| --------------- | --- | ----- |
| `ItemReady` | `Bool` | коробка на приёмной ленте (нормализованный S1) |
| `AtEntry` | `Bool` | коробка в зоне загрузки буфера (нормализованный S2) |
| `AtExit` | `Bool` | коробка в зоне выгрузки (нормализованный S3) |
| `EntryWork` | `Bool` | лента 1 работает |
| `BufferWork` | `Bool` | лента 2 работает |
| `BufferCount` | `Int` | коробок на буфере, `0…BATCH_SIZE` |
| `Count` | `Int` | всего выгружено коробок |

Требования:

1. Лампы и числовые поля панели **не занимают** физические выходы ПЛК: это поля DB, у них нет адреса `%Q`.
2. `EntryWork` / `BufferWork` — копии команд лент (`CmdEntry`, `CmdBuffer`), а не состояние датчиков.
3. `BufferCount` показывает текущее содержимое буфера, включая момент выгрузки; обнуляется только
   по завершении партии — оператор видит, сколько коробок уехало.
4. `Count` — накопительный, кратен `BATCH_SIZE` при штатной работе; сбрасывается при STOP→RUN.
5. Кнопок и команд с панели в задании нет: пуск и останов выполняет сама линия по датчикам.
   Кнопки «Стоп», аварийный останов и квитирование — вне объёма (раздел 14).
6. Других писателей в `"Hmi_DB"` нет; панель читает поля, но не пишет их.

## 7. Структура программы и репозитория

### 7.1 Блоки и порядок вызовов

```text
ProgramCycle (OB1)
└── "ConveyorMain_DB"()                       ← оркестратор
    ├── #hardIn  : "HardwareInput"            ← 3 НЗ-датчика → ItemReady, AtEntry, AtExit
    ├── #logic   : "LogicBatchBuffer"         ← состояния, межблокировки, счётчики, таймер
    │   └── #entryLatch : "LogicTirggerStartStop"  ← самоподхват ленты 1 (multi-instance)
    ├── #hardOut : "HardwareOutput"           ← CmdEntry, CmdBuffer → DO_*
    └── #hmi     : "HMIInterface"             ← 7 полей → "Hmi_DB"
```

| Блок | Ответственность | Не делает |
| ---- | --------------- | --------- |
| `ProgramCycle` | вызов оркестратора | ничего больше |
| `ConveyorMain` | порядок слоёв, передача данных между ними | не читает и не пишет теги и DB |
| `HardwareInput` | чтение `DI_*`, инверсия НЗ | ничего не пишет |
| `LogicBatchBuffer` | состояния `Idle/Fill/Discharge`, команды лент, счётчики, таймер | не знает про теги и DB |
| `LogicTirggerStartStop` | RS-триггер с приоритетом сброса (самоподхват) | не содержит технологической логики партии |
| `HardwareOutput` | запись `DO_*` | ничего не читает |
| `HMIInterface` | запись полей `"Hmi_DB"` | не читает теги поля |

## 8. Развёртывание в TIA Portal V19

Репозиторий содержит **не проект, а экспортированные исходники**. Проект создаётся в TIA Portal
и наполняется ими.

1. **Создать проект**: TIA Portal V19 → `Project → New…` → указать папку и имя `TiaPortalLab` → `Create`.
2. **Добавить контроллер**: `Devices & networks → Add new device → Controllers → SIMATIC S7-1200 →
   CPU 1212C DC/DC/DC → 6ES7 212-1AG40-0XB0 → OK`.
3. **Проверить адреса I/O**: в `Device view` выделить CPU → `Properties` → адреса встроенных DI/DQ.
   Они должны совпадать с `PLCTags.xml` (`%I0.0…%I0.2`, `%Q0.0…%Q0.1`).
4. **Импортировать теги**: `PLC_1 → PLC tags → Show all tags` → ПКМ → `Import…` → выбрать
   `PLCTags.xml` → `OK`.
5. **Импортировать блоки**: `PLC_1 → External source files` → `Add new external file` → выбрать
   `ConveyorObject\*.scl`, `ConveyorObject\Logic\*.scl`, `ConveyorObject\*.db`, `ProgramCycle.scl` →
   ПКМ по каждому файлу → `Generate blocks from source` → `OK`.
   Порядок важен: сначала FB (`HardwareInput`, `HardwareOutput`, `LogicTirggerStartStop`,
   `LogicBatchBuffer`, `HMIInterface`, `ConveyorMain`), затем global-DB (`Hmi_DB`), затем
   single-instance DB (`ConveyorMain_DB`), затем OB (`ProgramCycle`). Если блок ссылается на
   несуществующий тип — TIA выдаст «тип не найден».
6. **Проверить нумерацию OB**: `ProgramCycle` должен быть циклическим организационным блоком **OB1**
   (в свойствах блока — «Program cycle»). В проекте не должно остаться двух циклических OB.
7. **Скомпилировать**: ПКМ по `PLC_1` → `Compile → Software (rebuild all blocks)` (или `Ctrl+B`).
   Ожидается 0 ошибок.
8. **Загрузить/симулировать**: `Online → Start simulation` (при установленном PLCSIM V19) →
   `Download to device → Hardware and software`; либо загрузка в реальный CPU по PROFINET.

## 9. Симуляция поля в Factory I/O

Датчики и механизмы имитируются в **Factory I/O**: среда пишет значения датчиков в ПЛК и читает
команды на двигатели. Поэтому у всех тегов I/O в `PLCTags.xml` открыты права `hmiVisible`,
`hmiAccessible`, `hmiWriteable` (`True`) — занижать их нельзя.

### 9.1 Карта сигналов (совпадает с `PLCTags.xml`)

| Сигнал Factory I/O | Направление | Тег ПЛК | Адрес | Тип |
| ------------------ | ----------- | ------- | ----- | --- |
| НЗ-датчик «коробка на приёмной ленте» | Factory I/O → ПЛК | `DI_SensorItemReady` | `%I0.0` | `Bool` |
| НЗ-датчик «начало буферной ленты» (P1) | Factory I/O → ПЛК | `DI_SensorAtEntry` | `%I0.1` | `Bool` |
| НЗ-датчик «конец буферной ленты» (P3) | Factory I/O → ПЛК | `DI_SensorAtExit` | `%I0.2` | `Bool` |
| Двигатель приёмной ленты | ПЛК → Factory I/O | `DO_CommandEntryConveyer` | `%Q0.0` | `Bool` |
| Двигатель буферной ленты | ПЛК → Factory I/O | `DO_CommandBufferConveyer` | `%Q0.1` | `Bool` |

### 9.2 Настройка

1. **Драйвер S7 (S7-1200/1500)**: в TIA у CPU включить `Properties → Protection & Security →
   Connection mechanisms → Permit access with PUT/GET communication from remote partner`; в Factory I/O
   сигналы привязываются к абсолютным адресам `I0.0…I0.2`, `Q0.0…Q0.1`.
2. **Драйвер OPC UA**: у CPU включить `OPC UA → Server` (FW ≥ 4.4), теги остаются с открытыми правами;
   в клиенте они доступны по именам.
3. **С PLCSIM V19**: сначала `Online → Start simulation`, затем подключение драйвера Factory I/O
   к виртуальному CPU.
4. НЗ-датчики: в Factory I/O используется **нормально замкнутый** контакт (значение `TRUE`, пока
   коробки нет), иначе логика будет инвертирована.
5. Сцена должна повторять геометрию из раздела 3.1: три позиции на буферной ленте, S2 в начале P1,
   S3 за P3. От длины зон зависит, сколько коробок влезает в буфер.

> Писать в `DI_*` может только Factory I/O, в `DO_*` — только программа. Двойная запись в один тег
> даёт «плавающие» ошибки.

## 10. Отладка и симуляция

1. `Online → Go online`; открыть блок — включить `Monitoring on/off` (иконка «очки»): видны текущие
   значения в коде.
2. **Таблица наблюдения**: `PLC_1 → Watch tables → Add new watch table`; добавить `"DI_SensorItemReady"`,
   `"DI_SensorAtEntry"`, `"DI_SensorAtExit"`, `"DO_CommandEntryConveyer"`, `"DO_CommandBufferConveyer"`,
   `"Hmi_DB"`, `"ConveyorMain_DB"`; нажать `Monitor all`.
3. **Modify now** — однократная запись значения (для тегов и полей DB). Названия кнопок зависят от
   версии/локализации TIA.
4. **Force** — принудительная запись: в TIA это force job, он переживает перезапуск мониторинга и
   снимается через `Force → Delete all force jobs` либо переводом CPU в STOP. Обязательно снимать
   после отладки — иначе поведение программы искажено.
5. **PLCSIM V19**: входы `%I` в реальном CPU перезаписываются образом входов, поэтому для эмуляции
   датчиков используйте SIM table в PLCSIM (или Force). Прямая запись в `%I` из таблицы наблюдения
   ожидаемого эффекта не даёт.
6. **Разбор партии**: держать в мониторинге `#state`, `#BufferCount`, `#AtEntryEdge.Q`, `#EmptyTimer.ET` —
   по ним видно, на каком шаге линия встала (например, `Discharge` с растущим `ET` означает, что
   S3 видит «коробку», то есть обрыв провода или коробка осталась на ленте).
7. **Trace** (S7-1200 поддерживает трассировку) — для разбора редких событий и дребезга датчиков.

## 11. Циклограммы

Схемы показывают **цепочку обработки одного шага**, а не физическое время: все слои вызываются в
одном цикле сканирования OB1, поэтому `1` столбец — условная единица времени (один шаг обработки).
Подписи строк короче имён тегов, соответствие — в таблице.

| Подпись | Сигнал в проекте |
| ------- | ---------------- |
| `S1_NC` | `DI_SensorItemReady` — сырой вход, НЗ (коробка = `0`) |
| `ItemReady` | нормализованный `DI_SensorItemReady` (выход `HardwareInput`) |
| `S2_NC` | `DI_SensorAtEntry` — сырой вход, НЗ |
| `AtEntry` | нормализованный `DI_SensorAtEntry` |
| `AtExit` | нормализованный `DI_SensorAtExit` |
| `EntryRun` | самоподхват ленты 1 (static в `LogicTirggerStartStop`) |
| `CmdEntry` | команда ленты 1 (выход `LogicBatchBuffer`) |
| `CmdBuffer` | команда ленты 2 (выход `LogicBatchBuffer`) |
| `Discharge` | признак состояния `Discharge` |
| `BatchReady` | `BufferCount >= BATCH_SIZE` |
| `AtEntryEdge` | импульс `R_TRIG` по `AtEntry` (один скан) |
| `BatchDone` | импульс конца выгрузки (`EmptyTimer.Q`, один скан) |
| `EmptyTimer` | `TON` «буфер пуст» |
| `DO_Entry` | тег `DO_CommandEntryConveyer` |
| `DO_Buffer` | тег `DO_CommandBufferConveyer` |
| `EntryWork` | `"Hmi_DB".EntryWork` |
| `BufferWork` | `"Hmi_DB".BufferWork` |

### 11.1 Приём коробки: самоподхват ленты 1 и останов по зоне загрузки


### 11.3 Завершение выгрузки по выдержке «буфер пуст»

```text
AtExit           ‾‾‾‾‾\______________________________________________________

EmptyTimer       __________/‾\_______________________________________________
                            ↓↑
Discharge        ‾‾‾‾‾‾‾‾‾‾‾\________________________________________________
                            ↓
CmdBuffer        ‾‾‾‾‾‾‾‾‾‾‾\________________________________________________
                            ↓|
BatchReady       ‾‾‾‾‾‾‾‾‾‾‾\________________________________________________
                            ↓|
BatchDone        ___________/\_______________________________________________
                             ↓
DO_Buffer        ‾‾‾‾‾‾‾‾‾‾‾‾\_______________________________________________
                              ↓
BufferWork       ‾‾‾‾‾‾‾‾‾‾‾‾‾\______________________________________________
```

Разбор:

- столбец 5: последняя коробка ушла из зоны выгрузки, `AtExit` падает;
- столбец 10: `EmptyTimer` отсчитал `EMPTY_TIME`. Фронт таймера — **не** шаг обработки: он наступает
  через выдержку, поэтому связь `AtExit` → `EmptyTimer` на схеме не показана, а столбец условный;
- столбец 11: в одном шаге логики снимаются `Discharge`, `CmdBuffer` и `BatchReady`, формируется
  импульс `BatchDone` — по нему счётчики обновляются (`Count += BufferCount`, `BufferCount := 0`);
- столбец 12: гаснут выход `DO_Buffer` и `EmptyTimer` (его `IN` стал `FALSE` вместе с выходом из
  состояния — иначе таймер остался бы взведённым на следующую партию);
- столбец 13: гаснет лампа `BufferWork`.

### 11.4 Легенда (канон)

`‾` / `_` — уровень сигнала (TRUE / FALSE); `/` — передний фронт (`0→1`), `\` — задний фронт
(`1→0`); новый уровень начинается со следующего столбца; `↓` — стрелка реакции сверху вниз,
`↑` — снизу вверх, стрелка всегда стоит на фронте сигнала-следствия; `|` — вертикальная
причинно-следственная связь по столбцу сигнала.

**Правило столбцов (универсальное, без привязки к именам):** `+1` столбец = следующий шаг обработки
по цепочке «вход → логика → выход»; сигналы одного шага меняются в одном и том же столбце; проверка
корректности схемы: столбец фронта-следствия = столбец фронта-причины + 1; все шаги выполняются в
одном цикле сканирования (OB1), поэтому `1` столбец — условная единица времени, а не отдельный скан.
